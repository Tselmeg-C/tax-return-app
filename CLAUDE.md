# CLAUDE.md

Conventions for Claude Code sessions in this repo. Read `plan.md` (design),
`_docs/process.md` (team process) and `_docs/adlc.md` (LLM feature lifecycle)
before starting a task.

## Rules

- dont log, print, publish, commit, leak any kind of credentials like password, tokens, internal data, privacy data etc.
- allowed to create pull requests when the criteria met, but leave them for me to merge.
- `backend/app/tax/` is pure (no I/O, no DB, no network); every tax rule change needs a golden test (tariff: `tests/tax/golden/`; deductions: a
  reference case in `tests/tax/reference/`, see "Deductions").
- Never log document contents or the Steuer-ID (not in logs, traces, metrics, fixtures or error messages).
- Never put request/response bodies, query strings, cookies, auth headers, the Steuer-ID or document contents in span attributes or log fields (spans are scrubbed and log keys redacted as a safety net only).
- Never run migrations at app or worker startup; they run only in Railway's pre-deploy step.
- Any LLM change (prompt, schema, model, provider, routing) needs an eval run; see `_docs/adlc.md`.
  Evals live in `backend/evals/` (`evals/README.md`); they never import `app.llm` directly (the
  `pipeline` predictor reaches it only through `app.pipeline`) and run offline in CI (`oracle` /
  `heuristic` / `replay` / `pipeline --provider fake`). A predictor needing a key is skipped
  (exit 0) without it.
- The repo is public: no real or anonymised-real document, and no recording or report from a
  private dataset (`evals/datasets_private/`, #39), is ever committed. Eval data is synthetic
  ("Muster" people / vendors, masked Steuer-ID and IBAN, generated by `evals/synth`).
  Once #9 has merged, changing the `Category`, `DocType` or `PaymentMethod` enums
  (`backend/app/domain/enums.py`) is an LLM schema change and needs an eval run too.
- LLM calls go only through `app.llm.get_router()` (`_docs/llm.md`). Never log
  `LLMResult.raw_text`, prompts, parts or `str()` of SDK exceptions; log `type(exc).__name__`.
  LLM output schemas carry money as strings with a pattern (never `float` / `Decimal`).
- Recorded LLM HTTP fixtures (`backend/tests/llm/fixtures/`) are synthetic only (public repo):
  fictional inputs, `req_test_…` / `resp_test_…` ids, no keys or org / project headers.
- After #9 has merged, changing `routing.yaml` defaults, `temperature`, the strict-schema
  conversion, the image downscale / PDF mode or the provider request shape in `app/llm/` is
  an LLM change that needs an eval run (`_docs/adlc.md`).
- Pipeline (#9, `_docs/pipeline.md`): prompts live in `backend/app/pipeline/prompts/vN/` and an
  existing version is never edited (copy to `vN+1`, add its hash to `prompts/LOCK.yaml`, eval run).
  Never send `original_filename`, e-mails, household / person names, ids or storage keys to the
  LLM. The pipeline never changes, deletes or adds tax items of a document with an
  `overridden_by_user` item. Tax rules stay in `app/tax/bill_rules.py` (pure, golden tests), never
  in a prompt. `needs_attention` always stores one `AttentionReason` code
  (`app/domain/enums.py`, priority = definition order; adding one is a migration).
- Query household-owned tables through `HouseholdScope` (`app/db/scope.py`), never with a bare `select`.
- Log DB errors by exception class name only (`type(exc).__name__`), never `str(exc)`:
  Postgres' `DETAIL` can contain plain column values (names, e-mail, amounts).

## Auth (rules from #5)

- Every api route requires a session by default (app-level `require_session` in
  `backend/app/api/deps.py`). The only public paths are in `backend/app/api/public.py`
  (`PUBLIC_PATHS`); `tests/auth/test_protection.py` fails for any other route reachable
  without a session. Use `SignedIn` / `Scope` (`app.api.deps`) in endpoints.
- `backend/app/auth/service.py` is the one place that queries `app_user` / `magic_link_token`
  / `user_session` without `HouseholdScope` (lookups by e-mail or token hash happen before a
  household is known).
- Every POST/PUT/PATCH/DELETE needs `X-Requested-With: belegbot` (CSRF, `403 csrf`), so the
  frontend calls the api only through `apiFetch` (`frontend/src/lib/api.ts`). New CSRF-exempt
  paths (e.g. #11's webhook) go into `CSRF_EXEMPT_PATHS` in `public.py`.
- Never log, trace or put into an error message: e-mail addresses, link or session tokens,
  their hashes, cookie values or the `next` path. Log user/session ids instead.
- Times come from the injectable clock (`app.auth.clock`, `create_app(clock=...)`).
- Local login: `uv run python -m app.db.seed`, start the api (`MAIL_BACKEND` defaults to
  `file` outside production) and `npm run dev`, request a link on `/login` for
  `owner@example.com`, then open the newest file in `backend/.dev-mail/` and paste its link. In Codespaces nothing extra is needed (#51): `APP_BASE_URL` defaults to the
  forwarded https URL, dev CSRF also accepts localhost origins (production: `APP_BASE_URL` only).
- Users (also in production, via `railway ssh --service api`; output shows masked e-mails):

  ```bash
  uv run python -m app.auth.cli bootstrap --household-name "Familie X" --email you@example.org
  uv run python -m app.auth.cli invite --email member@example.org [--role member|owner] [--household-id ID]
  uv run python -m app.auth.cli disable|enable|revoke-sessions --email member@example.org
  ```

  `disable` never touches documents; there is no `delete` command.

## Passkeys (rules from #12)

- Ceremony logic in `app/auth/passkeys.py` (`webauthn` lib, one dependency), routes in
  `app/api/passkeys.py`. RP ID = hostname of `APP_BASE_URL`, expected origin = `settings.app_origin`
  (no new env var; changing the host orphans passkeys, `_docs/deploy.md`).
- Challenges are stateless: an HMAC-signed 5 min token in an httpOnly `SameSite=Strict` cookie
  (`__Host-belegbot_passkey`), purpose `register|login` (+ user id for register), cleared after use.
  The key is per process (`app.state.passkey_key`). No challenge table; a finished ceremony puts its
  challenge into an in-memory used set (`app.state.used_challenges`, TTL-pruned, same lifetime as the
  key), so a copied cookie cannot be replayed (#105). `userHandle` (when present) must be the owner's
  user id. `register/verify` locks the user row before counting (limit of 10 holds in parallel).
- Discoverable login (`residentKey=required`, `userVerification=required`, attestation `none`).
  `/auth/passkey/login/options` and `/login/verify` are in `PUBLIC_PATHS`; register / list /
  rename / delete need a session. Every login failure (unknown credential, disabled user, bad
  signature / origin / RP id, expired challenge, sign count not increasing) is the same
  `400 invalid_passkey`. Success uses `open_session` (`app/api/auth.py`), the same as the magic link.
- `passkey` table: `credential_id` / `public_key` are plain (public); lookup by credential id is in
  `app/auth/service.py` (no scope, before a household is known); everything else through
  `HouseholdScope` + the current user (other user's passkey = 404). Max 10 per user (`409
  passkey_limit`). Audit rows (`create` / `update` / `delete`) hold ids only: `name`,
  `credential_id`, `public_key`, `transports` are in `REDACTED_COLUMNS["passkey"]`.
- Never log or trace credential ids, public keys, challenges, client data, signatures, the challenge
  cookie, passkey names or `str(exc)` of the lib (`type(exc).__name__` only).
- Tests use the software authenticator `backend/tests/auth/authenticator.py`. Frontend: only
  `lib/passkeys.ts` via `apiFetch`; passkey UI is hidden without `PublicKeyCredential`.

## Member management (rules from #34)

- `app/api/users.py`: `/users*` (owner only, `403 forbidden` for members) and own sessions
  `GET /auth/sessions`, `DELETE /auth/sessions/{id}` (every user). All queries via `HouseholdScope`
  (another household's id = `404 not_found`). Web and CLI share `app.auth.service`
  (`create_user`, `set_disabled`, `revoke_user_sessions`, `invalidate_unused_tokens`); add new
  behaviour there, not in both places.
- Guard: demoting or disabling the last active owner is `409 last_owner` (ALL active owners, target
  included, are locked `FOR UPDATE ORDER BY id` and the target reloaded, so two owners acting on each
  other serialise instead of deadlocking; never make the lock set depend on the target).
  Decisions (#119, unchanged): `409 email_taken` on invite / e-mail change tells an owner that an
  address exists in any household (acceptable for a private family app, the CLI does the same); login
  and change links share one per-address limit (`email_limit_reached`). Disabling never touches documents; there is no delete.
- E-mail change: `PATCH /users/{id}` `{email}` stores a `magic_link_token` with `new_email` and mails
  the NEW address; `POST /auth/confirm-email` (public, token = proof) applies it, ends all sessions
  of the user and burns their links. Login links (`new_email IS NULL`) and change links are not
  interchangeable; a login burns only login links (`invalidate_unused_tokens(kind="login")`).
- Every change = audit row with actor = the owner (`app_user.email` is redacted in audit rows).
  Logs / spans carry user and session ids and codes only, never e-mail addresses or tokens.
- Frontend: `AccessCard` (owner only, Haushalt page) and "Angemeldete Geräte" (Einstellungen).

## Files, queue and worker (rules from #6)

- Everything that touches uploaded files goes through a `Storage` (`app/storage/`,
  `LocalVolume` under `STORAGE_PATH`); nothing else reads or writes document files. Keys are
  opaque (`households/<h>/documents/<d>/original`).
- `document.original_filename` is display metadata (sanitised by
  `app.documents.filenames.sanitize_filename`). Never use it in a path or a `Storage` call,
  and never log, trace or meter it (or the `X-Filename` / `Content-Disposition` headers).
- Never log file bytes or `str(exc)` from storage or job handlers; log `type(exc).__name__`
  (jobs store the class name, or `PermanentJobError.error_kind`, in `last_error_kind`).
- Job handlers (`app/queue/handlers.py`) must be idempotent (a job can run again after a crash
  or a lost lease) and raise `PermanentJobError` for non-retryable failures; the runner sets
  the document status. Enqueue with `app.queue.enqueue` inside the caller's transaction.
- Paths that change a document and its job lock the `document` row before the `job` row.
- Run the worker locally with `PORT=8000 uv run honcho start -f Procfile` (api + worker) or
  `uv run python -m app.worker`. Sweep: `uv run python -m app.storage.sweep [--dry-run]`.
  Queue ops: `uv run python -m app.queue.cli stats | retry <job_id>` (ids and counts only).

## New tables (rules from #4)

Every new table gets its own Alembic migration in the issue that first uses it. The
meta-tests in `backend/tests/domain/` check most of these rules automatically.

- `household_id uuid NOT NULL` → `household.id ON DELETE RESTRICT` on every table except
  `household` (use the `HouseholdOwned` mixin). An exception needs an entry with a reason in
  `HOUSEHOLD_ID_EXEMPT` (`tests/domain/test_schema_meta.py`)
- `id` via `UUIDPrimaryKey` (Python `uuid4`, no server default); timestamps via `CreatedAt` /
  `Timestamps`; money `Numeric(12, 2)`, never float
- Every FK column is the first column of an index (`Index(None, "col")` or a composite)
- Enums: `enum_type(MyEnum, "<column>")` from `app/db/types.py` (VARCHAR + CHECK storing the
  values, not native PG enums). Values are lowercase ASCII codes; German labels go in `LABELS_DE`
- Steuer-ID, IBAN, raw document text / LLM output: `EncryptedString("<table>.<column>")` or
  `EncryptedJSON(...)`. They cannot be filtered, compared or made unique
- Changes users make get an audit row via `app.db.audit.record(...)` (inside the caller's
  transaction; encrypted values are stored as `"[redacted]"`)
- Never override `__repr__` / `__str__` on models (they print `<Class id=…>` only)
- Migrations must not import from `app.*`: write enums as `sa.String(64)` + `sa.CheckConstraint`
  and encrypted columns as `sa.LargeBinary()`; write `downgrade()` by hand
- Test data uses fictional names and runtime-generated sentinels (never a real-looking Steuer-ID)

## Tax engine (rules from #14)

- Params: one file per year, `backend/app/tax/params/{year}.yaml`. Top-level sections are
  owned by issues and only their owner edits them: `year`, `mapping` (#9); `tariff`, `soli`,
  `church_tax` (#14); Werbungskosten / Sonderausgaben / agB / § 35a (#15); Vorsorge / Kinder /
  Progressionsvorbehalt (#16); `filing` (Abgabefristen, #92). Every section has a `source` (paragraph + BGBl. or official
  page); `provisional: true` (+ reason in `source`) marks a value not confirmed against the law.
- Money and rates are quoted strings in the YAML (`"0.42"`), `Decimal` in code; an unquoted
  number fails to load. Never `float` anywhere in the tax path.
- I/O only in `backend/app/tax_params.py` (`load_params(year)`, `supported_years()`); the
  models are in `app/tax/models.py`. `app/tax/` is pure: `tests/tax/test_purity.py` enforces
  an import allowlist, no `open`, no float literal / `float`.
- Golden tests (`tests/tax/test_golden_tariff.py`) compare with the BMF Einkommensteuerrechner
  at tolerance 0 (ESt to the euro, Soli to the cent). Expected values come only from the
  calculator, never from the engine; collect / re-verify them with
  `uv run python -m tests.tax.golden.collect --year YYYY` (`tests/tax/golden/README.md`).

## Deductions (rules from #15)

- `app/tax/deductions/` (pure, same purity test as the rest of `app/tax/`) works on frozen DTOs
  (`ReturnContext`, `ItemInput`, `EmploymentInput`, `ChildInput`, `models.py`) and `TaxParams`;
  #17 builds them from the DB. Ids are `str`. A float, NaN / infinite `Decimal`, negative
  count or an item `year` other than the context's raises (`TypeError` / `ValueError`).
- Order of calls: `werbungskosten` -> (#17: Gesamtbetrag der Einkuenfte) -> `sonderausgaben(gde=...)`
  -> `agb(gde=...)` (#76) -> (#17: zvE, tariff) -> `haushaltsnahe` (#77, off the tariff tax).
- Item selection (`select.py`, shared with #76 / #77): I1 wrong year raises; I2 `is_relevant = false`
  ignored; I3 person = taxpayer / spouse, `None` or a child = household-level, anyone else
  `person_not_in_return`; I4 `overridden_by_user` always counts, unreviewed (`attention_reason`)
  counts with `included_unreviewed` except `implausible_amount` / `sum_mismatch` / `sign_mismatch`
  (`excluded_attention`); I5 only the categories of the group; I6 net per (person, category),
  negative -> 0 + `net_negative_clipped`; I7 order never matters (notes are sorted).
- Notes are `DeductionNote` codes with item / person ids (`Note`), never amounts or names.
  Adding one needs a `LABELS_DE` entry; no DB column, no migration.
- Rounding: exact `Decimal`; a share of an amount in cents (80 %, 30 %, 20 %) rounds down to
  cents; nothing else is rounded.
- Params sections `werbungskosten` and `sonderausgaben` belong to #15. `union_dues_beside_pauschbetrag`
  (true from 2026) is `§ 9a Satz 3`: Gewerkschaftsbeitraege (`wk_berufsverband`) are added on top of
  the Pauschbetrag comparison. `provisional: true` marks a value not read in the law text;
  `TaxParams.provisional_sections` lists them for "vorlaeufig" in the UI.
- Golden tests for deduction rules are the hand-computed cases in `tests/tax/reference/`
  (`{werbungskosten,sonderausgaben}_{year}.yaml`): each has `source` (paragraph), `arithmetic` and
  `expected`, computed by hand from the law text and never with the engine. A rule or value change
  needs a new or changed case for every year it applies to, and a case changes only together
  with its `arithmetic`. They prove our reading of the law, not the reading (README there).
- Not applied in v1 (own issues): 4 500 EUR commute cap (#74), doppelte Haushaltsfuehrung limits
  (#73), the Pauschbetrag limit by the wage (`§ 9a Satz 2`, #17), Spendenvortrag (#74).

## § 35a (rules from #77)

- `app/tax/deductions/haushaltsnahe.py`: `haushaltsnahe(ctx, items, params.haushaltsnahe)`. It is a
  Steuerermäßigung: #17 subtracts `total` from the tarifliche Einkommensteuer (`min` with that tax,
  no carry-over), never from the income; Soli / KiSt follow from the reduced ESt (#17).
- Per category `min(cap, 20 % x labour sum)`, rounded down to cents; caps 4 000 (Abs. 2) and
  1 200 (Abs. 3) are independent, one pair per return. Item amount = `min(deductible_amount,
  labour_share_35a)`; NULL share -> 0 + `labour_share_missing`.
- Cash (`payment_method = cash`) is excluded whatever `is_relevant` / overrides say (Abs. 5 Satz 3),
  note `cash_excluded`; `unknown` / `other` count with `payment_unverified`.
- Reference cases: `tests/tax/reference/haushaltsnahe_{year}.yaml`. Minijob (Abs. 1) is #75.

## Vorsorge (rules from #16)

- `app/tax/deductions/vorsorge.py`: `vorsorge(ctx, persons, params.vorsorge)` is a pure function on
  `VorsorgeInput` (final amounts per person: `rv_employee`, `rv_employer | None`, `basisrente`, `kv`,
  `pv`, `sonstige`, `employed`; exactly the persons of the return). `vorsorge_from_items` fills the
  DTO from tax items with #15's rules I1 to I7 (`vorsorge_rv`, `_ruerup`, `_kv_pv`, `_sonstige`;
  `vorsorge_riester` is skipped with `riester_not_supported`, #82). Its result (`total`) is added to
  #15's `sonderausgaben(...).applied`; the Pauschbetrag of § 10c does not cover it.
- Amounts of an official source (#18 Lohnsteuerbescheinigung, `official_record`) or a manual value
  replace the item sum per field; never use both (the contribution would be counted twice). #17
  decides the source, not this module.
- v1 `employed` (the person has an employment that year): Höchstbetrag 1.900 EUR (else 2.800), 4 %
  Krankengeld cut on `kv` (rounded down to cents), employer pension share = employee share when
  `rv_employer is None` (`employer_share_assumed`). With that assumption the Altersvorsorge `abzug`
  is not monotone above the Höchstbetrag. `vorsorge_kv_pv` is not split (`kv_pv_unsplit`): the cut
  also hits the PV part (#84). No Abs. 3 Satz 3 Kürzung (Beamte), no Erstattungsüberhang (#84).
- Pooling (joint): amounts add up, the Höchstbetrag doubles (Abs. 3 Satz 2), the 1.900 / 2.800 cap
  is the sum per spouse (Abs. 4 Satz 3) and Abs. 4 Satz 4 ("Nr. 3 above the cap excludes Nr. 3a")
  is applied once to the pooled sums, so joint can be lower than two single returns (case K9).
- No Günstigerprüfung and no Vorsorgepauschale: § 10 Abs. 4a EStG applies to 2013 to 2019 only, § 39b
  is Lohnsteuer withholding. Do not add a code path.
- Params section `vorsorge` belongs to #16. Höchstbetrag = knappschaftliche BBG (§ 4 SVBezGrV) x
  Beitragssatz 24,7 % (RVBeitrSBek), rounded up: 29.344 (2025), 30.826 (2026). A new year needs both
  inputs read from the law, not from memory.
- Golden tests: `tests/tax/reference/vorsorge_{year}.yaml` (hand-computed, as in #15) plus property
  tests; no official calculator exists for Vorsorge.

## Progressionsvorbehalt (rules from #86)

- `app/tax/progression.py` (pure): `tariff_with_progression(zve, filing, lohnersatz, tariff, p)`
  returns the tarifliche ESt in full euros with the besonderer Steuersatz (§ 32b Abs. 2 Nr. 1):
  `floor(x * ESt(floor(x + lohnersatz)) / floor(x + lohnersatz))`, tariff from `income_tax`
  (never copy the zone formulas). `lohnersatz = 0` equals `income_tax`. `filing` must be a
  `FilingStatus` member (a string raises `TypeError`).
- The rounding of the rate is OPEN: the law text has no rule and no minimum rate; v1 is exact.
  `progressionsvorbehalt.rate_decimals` (`"exact"` or `"0"`..`"8"`) switches it without code
  change once the Finanzverwaltung rule is found; the section stays `provisional: true` until then.
- `progression_amount` deducts the Arbeitnehmer-Pauschbetrag (`werbungskosten.arbeitnehmer_pauschbetrag`,
  never a literal) once per person, only the part not used against wages (§ 32b Abs. 2 Nr. 1).
- Reference cases: `tests/tax/reference/progressionsvorbehalt_{year}.yaml` (hand-computed). BMF
  building blocks: `tests/tax/golden/blocks_{year}.yaml` (`bmf: null` = pending, see its README).

## Kinder and assessment (rules from #87)

- `app/tax/kinder.py` (pure): `kinder_amounts` and `guenstigerpruefung(zve, children, filing, est_fn,
  kinder_params, year=)`; `app/tax/assessment.py`: `festsetzung(zve_before_children, ctx, state,
  lohnersatz, children, ermaessigung_35a, params)`. Params section `kinder` (Freibeträge are
  per parent; `provisional: true`, the two unconfirmed readings are named in its `source`).
- #13 fields: `months` (0..12) = Zwölftelung of Kinderfreibetrag + BEA and of the Kindergeld
  (`months = 0`: child ignored); `allowance_share` (`ChildInput.allowance_half`): full = both
  parents' halves (x2), half = one half, the Kindergeld in the comparison follows the same share
  (§ 31 Satz 4); `in_household` is not used here (#15 Kinderbetreuung, #81).
- Günstigerprüfung (OPEN reading): child by child, larger Freibetrag first (then dob, person_id);
  the Freibetrag only if it saves STRICTLY more than the child's Kindergeld, a tie keeps Kindergeld.
  The law text does not state the order for several children; no R 31 EStR read. Used children add
  their Kindergeld to the tarifliche ESt.
- Bemessungsgrundlage of Soli / KiSt (§ 51a Abs. 2 EStG, § 3 Abs. 2 SolzG): ESt with ALL
  Freibeträge (also where Kindergeld was chosen), without the Kindergeld addition, minus § 35a;
  Soli / KiSt are `solidarity_surcharge(bmg)` / `church_tax(bmg)`, never of the tax.
- § 35a (arrives as a plain number from #77) is capped by the tarifliche ESt including the
  Kindergeld addition (OPEN reading, unused part lost); agB (#76) arrives inside the zvE.
- Chain (what #17 calls): werbungskosten -> Einkünfte -> minus Entlastungsbetrag (#81) = GdE ->
  sonderausgaben + vorsorge -> agB -> zvE before children (>= 0) -> `progression_amount` ->
  `festsetzung` -> minus Lohnsteuer / Soli / KiSt withheld. `ctx.year` must equal `params.year`.
- Golden tests: `tests/tax/reference/{kinder,festsetzung}_{year}.yaml` (hand-computed, never from
  the engine; the 2025 issue figures are literals in `test_assessment.py`). The Günstigerprüfung,
  the Kindergeld addition, the § 35a cap and KiSt cannot be checked with the BMF calculator.
- Notes: `child_over_25_disabled` (disabled child over 25, `months` trusted) and `child_age_review`
  (over 25 without grade, counted as given). Results and notes carry ids and codes only.

## Household api decisions (#78)

- Employments of a person not in the return (greyed) are read-only (`422 person_not_in_return`
  on PATCH), but can be deleted. A child row (`PUT /household/{year}/children/{id}`) needs a
  `tax_profile` for that year (`409 profile_missing`); `copy` always creates the profile first.

## Previews (rules from #35)

- `preview.jpg` (JPEG, long side <= 400 px, upright, no EXIF / GPS) sits next to the original at
  `app.storage.preview_key(h, d)`; written only through `Storage` by `app.documents.previews.ensure_preview`.
  Decoding is `app.pipeline.preprocess.preview_jpeg` (same decoders and error kinds as the pipeline).
- Generated as a best-effort step at the start of the `process_document` job (no extra queue job):
  it never raises, never fails or delays the tax processing beyond one decode, logs only
  `type(exc).__name__`, and leaves no file for a corrupt document. Existing previews are kept
  (reprocess does not regenerate). Delete removes it with the document directory.
- `GET /documents/{id}/preview`: same scoping as `/file`, `404 preview_not_found` until it exists.
  Frontend: `DocThumb` (`<img>` with the session cookie, alt text never holds the file name).
- Backfill: `uv run python -m app.documents.previews [--dry-run]` (idempotent, ids / counts only).

## Tax items and overrides (rules from #10)

- Every user write to `tax_item` goes through `app/tax_items.py` (`update_item` /
  `create_manual_item`): it sets `overridden_by_user` (the pipeline never touches such an
  item), checks `version` (`409 version_conflict`), locks the `document` row before the
  `tax_item` row (`409 document_busy` while queued / processing), writes exactly one
  `tax_item` audit row (+ one `document` row when it resolves "needs attention") and emits
  `belegbot.tax_item.*` counters only after the commit.
- `anlage` / `zeile` are never edited: they follow `load_params(year).mapping`.
- Money is a dot-decimal string on the wire (`^-?\d{1,9}\.\d{2}$`); the frontend parses
  German input with `parseEuroInput` (`frontend/src/lib/money.ts`). Error bodies are a code
  plus the field name, never the sent value.
- Never log, trace or meter override values (amounts, vendor, `reason`, names): log events
  carry ids, field names and codes only.
- Audit rows never hold `tax_item.vendor` / `reason` (`REDACTED_COLUMNS` in `app/db/audit.py`; the changed-field keys stay).
- The UI takes enum labels only from `GET /meta/labels` (no copy of `LABELS_DE` in the frontend).
- #61: PATCH also takes `vendor` (trimmed, max 200), `invoice_date`, `payment_date` (ISO, 2000..2100)
  and `payment_method`; they are stored only (`year`, `is_relevant`, `deductible_amount` are never
  re-derived; a payment year != tax year is a UI hint only). `payment_method` is a tax input
  (`cash` drops a § 35a item), vendor / dates stay out of the estimate hash. Codes: `invalid_text`,
  `invalid_date`, `invalid_payment_method`, `vendor_required`, `delete_not_allowed`. Text, dates and
  method are `Any` in the request models so the service answers code + field. `POST /tax-items`
  (no document, `vendor` required) and `DELETE /tax-items/{id}?version=` (only `document_id IS NULL`,
  else `409 delete_not_allowed`) go through `create_manual_item(document_id=None)` / `delete_item`.
  `tax_item.vendor` / `reason` are redacted in audit rows (`REDACTED_COLUMNS`).

## Household and profile (rules from #13)

- One return per household and year: `tax_profile` (`UNIQUE (household_id, year)`) names the
  taxpayer and, for `joint`, the spouse. Persons are household-wide; `tax_profile`,
  `employment` and `child_year` are per year. Every per-year route answers `422
  unsupported_year` for a year outside `supported_years()` (never a 500).
- Every write to `person`, `tax_profile`, `employment` and `child_year` goes through
  `app/household/service.py` (one audit row per changed row, in the caller's transaction);
  the rules live in `app/household/validation.py` (pure, `422 {"detail", "field"}`, never the
  sent value).
- Steuer-ID: optional, write-only, validated only in `app/household/validation.py` (11 digits,
  digit-repeat rule, ISO 7064 MOD 11,10). Responses carry `steuer_id_masked`
  (`XX XXX XXX 901`) only; the duplicate check decrypts in memory, never in SQL. Never in logs,
  spans, metrics, error bodies, audit rows (`[redacted]`), URLs, the frontend query cache or an
  LLM call (a static test checks `app/pipeline/`, `app/llm/`, `evals/`). Tests use IDs from the
  runtime generator (`tests/household/steuer_ids.py`), never a fixed literal.
- Audit rows never hold names, dob or employer: `REDACTED_COLUMNS` in `app/db/audit.py` stores
  `"[redacted]"` for them (the key still shows which field changed); add a column there when a
  table gets new plain-text personal data.
- `Bundesland` codes are lowercase; `bundesland.value.upper()` is the key of
  `params/{year}.yaml` → `church_tax.rate_by_state`. Church tax is derived from
  `person.religion` + params at calculation time, never stored.
- Deleting a person never deletes tax items, documents or logins: `409 person_has_tax_items`
  / `409 person_in_profile`, otherwise only that person's `employment` / `child_year` rows go
  (each with a `delete` audit row).
- The Haushalt wizard (Du, Veranlagung) is first-time setup only and keeps no state of its own:
  it shows while the year has no `tax_profile`; a saved profile counts as set up and employers /
  children are added on the page view. The step is derived from
  `GET /household/{jahr}`. Household writes in the frontend are plain `apiFetch` calls (no
  `useMutation`), so a typed Steuer-ID never lands in the query or mutation cache.

## Estimate (rules from #17)

- `app.estimate.service.build_summary(scope, year, today)` is the only place the estimate is
  computed (web `GET /summary`, bot #11 calls it too). It calls the pure engines of `app/tax/`
  in the order of #17, never computes tax itself and returns a JSON-ready dict (money as
  dot-decimal strings, codes only). Compute on read, no job; the `estimate` row is a snapshot
  per `(household, year, inputs_hash)` (`ON CONFLICT DO NOTHING`), never served.
- Refund sign: positive = Erstattung, negative = Nachzahlung (UI says "Nachzahlung", never a
  negative "Erstattung"). Refund = Lohnsteuer + Soli + KiSt withheld - (festzusetzende ESt +
  Soli + KiSt). Kindergeld is not part of it (`kindergeld_added` is shown separately).
- Manual inputs until #18: `employment.gross_wage / lohnsteuer / soli_withheld /
  kirchensteuer_withheld / rv_employee / rv_employer / basisrente / kv / pv /
  sonstige_vorsorge` (NULL = not entered, `copy_year` never copies them) and the `lohnersatz`
  table (`PUT|DELETE /household/{year}/lohnersatz/{person_id}`). Amounts are audited, never
  logged, never in span attributes or error bodies (`invalid_amount` + field name only).
- Vorsorge is never counted twice: per person a group with any employment field set
  (RV: `rv_employee`/`rv_employer`, KV/PV: `kv`/`pv`, `basisrente`, `sonstige_vorsorge`)
  replaces the matching item categories entirely; otherwise `vorsorge_from_items`; neither =
  0 + `vorsorge_missing`.
- Only the Arbeitnehmer-Pauschbetrag is limited by the wage (§ 9a); real Werbungskosten may
  exceed it. Pass a real `FilingStatus` member; `state = bundesland.value.upper()`, `None` when
  nobody in the return is a church member. Persons outside the return are ignored.
- `person_vorsorge` (#98, `PUT|DELETE /household/{year}/vorsorge/{person_id}`, whole row, at least one
  field else `empty_vorsorge`) holds the Vorsorge fields of a person in the return, meant for one
  without employment (the UI card shows only then). Per group (RV, KV/PV, Basisrente, Sonstige)
  the precedence is person row > employment fields > items; sources are never summed. `employed`
  stays derived from employments. `copy_year` does not copy it.
- Pflichtveranlagung gets employment rows only for persons whose wage is not 0 (an entered
  wage of 0 means no wage; a wage not entered yet counts as a wage). The § 108 Abs. 3 AO shift
  (`app/estimate/deadlines.py`) and `overdue` are applied at display time only: the stored
  `estimate.result` holds the statutory `deadline_statutory`.
- KAP / Anlage V (#19 / #20) are 0 (Entlastungsbetrag: see #81); items of those groups only
  produce `kap_v_not_supported` in `what_missing`.
- Golden service scenarios: `backend/tests/estimate/scenarios/golden_2025.yaml` (hand-derived
  chain per line) + `bmf_inputs_2025.yaml` (BMF values only, refresh with
  `uv run python -m tests.estimate.collect_bmf --year 2025`, needs the `golden` group).

## Bot (rules from #11)

- `app/bot/core.py` is channel-agnostic (no `telegram` import, a static test checks it): adapters map
  updates to `IncomingMessage` and implement `ChannelAdapter` (`send_text`, `open_file` streaming,
  `delete_message`). The Telegram adapter (`app/bot/telegram.py`) is plain `httpx`, no bot framework.
  Texts live in `app/bot/messages.py` (German), `/summary` and `/missing` render `build_summary` only
  (`app/bot/render.py`); the bot never computes tax.
- `app/bot/links.py` is the second place (after `app/auth/service.py`) that queries `channel_link`,
  `channel_link_code` and `app_user.disabled_at` without `HouseholdScope` (lookup by chat hash / code
  hash before a household is known). Everything after the lookup uses `HouseholdScope(session,
  link.household_id)`.
- Never log, trace or meter: message text, file bytes / names, chat ids, Telegram user ids / names,
  update payloads, link codes (or their hash), tokens, the webhook secret or path, Bot API URLs (the
  download URL contains the token). Log user / household / document ids, the command name (fixed set),
  outcome codes and `type(exc).__name__`. `TelegramError` carries the Bot API method name only.
  Replies to the linked chat may hold amounts and vendors; logs never.
- Webhook `POST /bot/telegram/{secret}` (public + CSRF-exempt by route template in `app/api/public.py`;
  `is_csrf_exempt` matches concrete paths): path secret wrong -> 404, header
  `X-Telegram-Bot-Api-Secret-Token` missing / wrong -> 403 (both `hmac.compare_digest`), then always
  200; the update is handled in a held task (`app.state.bot_tasks`, tests await it). The request log
  and spans use the template (`ScrubbingSpanProcessor` masks the secret segment in `url.path` etc.).
  Registered at `<APP_BASE_URL>/api/bot/telegram/<secret>` through the web proxy (it forwards the
  header). Secret charset `[A-Za-z0-9_-]{16,256}`; production webhook mode needs `TELEGRAM_BOT_TOKEN`
  and `TELEGRAM_WEBHOOK_SECRET` (`replace-me` counts as unset).
- Private chats only; groups, channels, edits and callbacks are dropped in `parse_update`. An unlinked
  chat gets no reply (only `/link <code>` is processed; `/start` answers the static help), a disabled
  user or a removed link gets nothing at all.
- Link codes: 8 digits, 10 min, single use, atomic `UPDATE ... RETURNING`, only `sha256` stored, a
  new code invalidates the user's open ones. `/link` limits: 5 failures / chat and 30 global per
  15 min (in memory); over the limit no reply and no check. `/link` with a code from a chat that
  already belongs to someone else burns the code (accepted, #107; issue a new one). The `/link` message is deleted (best
  effort). Relinking replaces the user's row (audit delete + create); `external_id` is encrypted,
  `external_id_hash` (`sha256("telegram:" + chat id)`) is the lookup key and is redacted in audit rows.
- One update at a time per chat (`asyncio.Lock` per chat hash, arrival order), `last_update_id` is
  claimed with a conditional `UPDATE` before handling: a repeated or older `update_id` is ignored, so
  a Telegram retry never runs `/undo` twice (a crash mid-update loses that update, never repeats it).
- Files: one `ingest_document(channel=TELEGRAM, original_filename=None, ...)` per file with the adapter
  stream (albums = separate updates, no cross-update state); `/undo` deletes the user's newest telegram
  document through `delete_document` and refuses one with an `overridden_by_user` item.
- Notifications run in the worker (`app/bot/notify.py`, subscribed in `app/worker/__main__.py` when
  `TELEGRAM_BOT_TOKEN` is set) on `DocumentProcessed`, telegram documents only, to the link of
  `document.uploaded_by_user_id`; errors are logged by class name and never raised.
- Local: `uv run python -m app.bot.poll` (polling, `BOT_MODE=polling`, not in the Procfile; deletes a
  registered webhook first), `uv run python -m app.bot.cli set-webhook|delete-webhook` (prints the
  host only). Tests use `FakeAdapter` / `httpx.MockTransport` only; chat ids, codes and secrets are
  generated at runtime.

## Entlastungsbetrag (rules from #81)

- `app/tax/deductions/entlastungsbetrag.py`: `entlastungsbetrag(ctx, children, shares_household, p)`
  (pure, `ChildInput` list as in #87). Taken off the Summe der Einkünfte (§ 24b Abs. 1), i.e. between
  Einkünfte and `sonderausgaben(gde=...)` / `agb(gde=...)`: `gde = einkuenfte - result.total`.
- Rules: only `single` filers (joint = 0); a child counts with `in_household` and `months > 0`;
  `tax_profile.shares_household_with_adult` (Haushaltsgemeinschaft with another adult, § 24b Abs. 3,
  a checkbox for `single` on the Haushalt page, audited, copied by `copy_year`) gives 0 + note
  `entlastung_household_shared`. 4.260 + 240 per further child (params section `entlastungsbetrag`,
  `provisional: true` because of the OPEN reading below, amounts same 2025 / 2026), Abs. 4: 1/12 per full month without the conditions.
- OPEN reading: the child with the most months carries the 4.260, each further child adds
  `240 x months / 12`. `in_household` is a year flag; `months` is the entitlement months, so a child
  that lived with the parent only part of the year is not modelled (enter `months` accordingly).
  Widowed Splitting (§ 32a Abs. 6) is #53; Steuerklasse II is not checked against the profile.
- Reference cases: `tests/tax/reference/entlastungsbetrag_{year}.yaml` (hand-computed, read by
  `tests/tax/test_entlastungsbetrag.py`); service scenario `s7_single_parent_entlastungsbetrag`
  (tariff from the BMF calculator). `GET /summary` carries `entlastungsbetrag`.

## Vorsorge estimate from the wage (rules from #85)

- `app/tax/sv_estimate.py` (pure): `estimate_sv(wage, params.sozialversicherung, children_under_25=,
  childless_surcharge=)` returns the employee shares RV (+ the same as `rv_employer`), KV, PV, ALV
  (ALV goes to `sonstige`, Nr. 3a) or `None` for a wage at or below 12 x `uebergangsbereich_upper_monthly`
  (Minijob / Übergangsbereich: other formula, no estimate). Each branch is capped by its BBG (RV and ALV
  `bbg_rv`, KV and PV `bbg_kv`) and rounded half-even to cents (the law has no rule for an estimate).
- Params section `sozialversicherung` belongs to #85: total rates (RV 18,6 %, ALV 2,6 %, KV 14,6 %,
  PV 3,6 %; the employee pays half) and the average Zusatzbeitrag (half), BBGs from the SVBezGrV of the
  year. A new year needs the BBGs, rates and Zusatzbeitrag read from the sources, not from memory. The
  section is `provisional: true` (secondary sources only, see its `source`); the Zusatzbeitrag is the
  Bundesdurchschnitt, never the person's Kasse.
- PV employee share: half the rate, + `pv_childless_surcharge` when the household has no child person at
  all and the person is not under 23, - `pv_child_abschlag` per child under 25 from the 2nd to the 5th.
  Ages are taken at 31 December (law: by month). The Sachsen PV split is not applied.
- `_vorsorge_inputs` order per group (RV, KV + PV, `sonstige`): person-level row > employment fields >
  items > estimate; sources are never summed. The estimate fills a group only when none of the others has
  a value, and then adds the note `vorsorge_estimated` (person id) and the summary field
  `vorsorge_estimated: [person_id]`; a person with an estimate is not in `vorsorge_missing`. The Übersicht
  shows the note with a link to Haushalt. The estimated amounts are part of `inputs_hash`.
- Golden tests: `tests/tax/reference/sv_estimate_{year}.yaml` (hand-computed, run by
  `tests/tax/test_sv_estimate.py`) and the estimate scenarios s8 / s9 in `golden_2025.yaml`.
- Not estimated (follow-up): Minijob / Midijob, Beamte, PKV, Rentner, Studenten, bAV, Zusatzbeitrag per person.

## Church tax, one member (rules from #53)

- `app/tax/church.py` (pure): `church_tax_joint(bmg, zve_bmg, MemberShare(member, total), state, p)`
  for a JOINT return with exactly ONE church member. KiSt = rate x Bemessungsgrundlage x member /
  total (Summe der Einkuenfte ratio, rounded down to cents). `festsetzung(..., church_member=None)`:
  `None` = old behaviour (whole base); the estimate service sets it only for joint + one member
  (member flags from `person.religion`, income = wage Einkuenfte per person, note
  `kist_share_estimated`). Result carries `kist_method` (`full` / `member_share` / `kirchgeld`),
  `GET /summary` adds `kirchensteuer_method` (additive).
- Params `church_tax.kirchgeld`: `stufen` (lower bound of the zvE after the Kinderfreibetraege ->
  annual amount), `compare_states` (higher of member-share KiSt and Kirchgeld is charged),
  `no_kirchgeld_states` (BY: share only). Any other Land: member share + note
  `kirchgeld_not_modelled`. A new Land needs its Kirchgeld text read first (source in `source`).
- What is confirmed and what not is in the params `source` (per Land, per year); the section stays
  `provisional: true`. Open: BW / BE / BB / MV / ST / HB / HH / HE / RP / SL / SH / TH tables, NW and NI
  2026 (Erlass not read), 8 % for BW / BY from secondary sources only. Out: Kappung #112,
  part-year #113, Witwensplitting #114, § 26a #115.
- Reference cases `tests/tax/reference/kirchensteuer_{year}.yaml` (hand-computed) +
  `tests/tax/test_church.py` (Stufe boundaries for SN / NW / NI). The Kirchenlohnsteuer already
  withheld is part of the refund sum, never netted inside the engine.

## Export (rules from #21)

- `GET /export/{year}.pdf|csv|zip` (`app/api/export.py`, `app/export/`) only renders
  `build_summary`; it never calls `app/tax/` and never computes a figure. `by_line`
  (`anlage, zeile, category, amount, item_ids`) is built in the same loop and by the same
  selection helper (`_counted`) as `by_anlage`, so the lines of an Anlage add up to its sum.
- No Steuer-ID, no person or employer name, no `original_filename` in any export: persons are role
  labels ("Steuerpflichtige/r (Person 1)", "Kind 1", "Haushalt"), a receipt is its "Beleg-Nr."
  (first 8 characters of the item id). Vendor text is the only free text (PDF: cut at 60
  characters, cp1252-safe, XML-escaped; CSV: leading `'` before `= + - @ TAB CR`).
- ZIP: entry names `<anlage>_<zeile>_<date>_<vendor>.<ext>` (ASCII, vendor slug, ext from the sniffed
  mime type, collisions `_2`), one file per document, originals only through `Storage.open`, a
  missing one is listed in `FEHLT.txt` + `X-Export-Missing` and never aborts. Cap
  `EXPORT_ZIP_MAX_MB` (default 500) -> `413 export_too_large` before any byte.
- Kapitalerträge / Vermietung items are listed under "Nicht in der Schätzung" (CSV hint
  `nicht_berechnet`), never in the estimate. Fixed download names, `Cache-Control: no-store`.
- Logs: `export.built` with `year, format, items, bytes, missing` only. PDF / CSV changes need
  `UPDATE_SNAPSHOTS=1 uv run pytest tests/export/test_snapshots.py` reviewed in the diff.
- `reportlab` is a runtime dependency (pure wheel, built-in Helvetica); do not add system packages.

## Reprocess (rules from #45)

- `app/documents/reprocess.py` (`reprocess_documents`) is the one place that re-queues a finished
  document ("Neu verarbeiten"): lock the `document` row (bulk in id order), status must be `done` /
  `needs_attention` / `failed` (else `busy`), any `overridden_by_user` item (mixed documents too)
  -> `has_overrides` (no job, no LLM call, nothing changes), then `enqueue` and one `document`
  audit row, all in the request's transaction. Status -> `queued`, `error_kind` / `attention_reason`
  cleared.
- `POST /documents/{id}/reprocess` (any member; `409 document_busy` / `has_overrides`) and
  `POST /documents/reprocess` (owner only, <= `REPROCESS_BULK_MAX` = 25 ids, `422 too_many`,
  duplicates `422`, never a 4xx per document: `{queued, skipped[{id, reason}]}`).
- `fresh` rides in the new `job.fresh` column (`ClaimedJob.fresh_since` = job `created_at`): the
  handler then reuses only extraction rows written by that job's own attempts; `fresh=false`
  reuses the same prompt version's cached steps (no LLM call). Extraction rows are append-only.
- Rate limit (3 bulk / 20 single requests per user and hour, `429` + `Retry-After`) is counted from
  `audit_log` rows whose `after` has the `reprocess` marker (`single` or `bulk:<request id>`); it
  uses DB `now()`, not the app clock. Do not drop that marker from the audit row. `retry_after`
  first takes `pg_advisory_xact_lock(hashtextextended('reprocess:<user id>', 0))`, so parallel
  requests of one user serialise until the holder commits; keep it before the count and in the
  same transaction as the audit rows.
- Metric `belegbot.documents.reprocess{outcome}`; logs carry ids, counts and `fresh` only.
- No ops CLI yet (follow-up issue). No eval run needed: pipeline, prompts, schema and routing are
  unchanged.

## CI

`.github/workflows/ci.yml` runs on every pull request (any base), on push to `main`
and on `workflow_dispatch`:

- `changes`: path filter. `backend` runs for `backend/**` or `.github/workflows/**`,
  `frontend` for `frontend/**` or `.github/workflows/**`; both run on `main` and manual runs
- `backend`: Postgres 16 service, `uv sync --locked`, ruff check, ruff format --check,
  `mypy app evals`, `alembic upgrade head` / `check` / `downgrade base` / `upgrade head`, pytest,
  `evals.validate --dataset bills_v0` and the offline oracle gate run (no secret, no network)
- `frontend`: `npm ci`, lint, typecheck, test, build
- `deploy-smoke`: (docker, GitHub runner only) builds both images, runs `alembic upgrade head`
  twice concurrently against a throwaway Postgres 16, starts api + web and curls `/health`,
  `/version`, `/healthz`, `/`, `/api/health`, `/api/version`, uploads a file through the web
  proxy onto a root-owned docker volume at `STORAGE_PATH` (job must reach `done`), then 502 with
  the api stopped; checks that honcho, uvicorn and the worker run with a non-zero uid. Runs for `backend/**`, `frontend/**`, `.github/**` changes and on `main`
- `ci-ok`: passes when every needed job succeeded or was skipped by the path filter,
  fails on any failure or cancellation. This is the only check branch protection needs

No repository secrets are used; the Postgres password in the workflow is a CI-only value.

Branch protection (recommended, applied by the repo owner in GitHub settings, not by
agents): protect `main`, require a pull request, require status check `ci-ok`, and
require branches to be up to date before merging.

## Env

Copy `.env.example` to `.env` (git-ignored) and fill in values locally; real
secrets live in Codespaces / Railway secrets, never in the repo.

`FIELD_ENCRYPTION_KEY` (encrypted columns) is a comma-separated list of Fernet keys: the
first encrypts, all decrypt (prepend a new key to rotate). The app, `/health` and Alembic run
without it; the first encrypt/decrypt of a non-NULL value raises `EncryptionKeyError`. Generate
a dev key with:

```bash
cd backend && uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Use a different key per environment and keep a backup: data encrypted with a lost key is
unrecoverable. Tests generate throwaway keys at runtime and need no key configured.
